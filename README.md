## Overview

### Session 1 — Trip Summary Generator (Console App)

A simple console application that collects trip details from the user and prints a formatted summary.

### Session 2 — Recommendation Engine (Layered Architecture)

The app is now split into a layered architecture:

- **`backend/services/trip_service.py`** — business logic layer. Contains the trip category, travel season, daily budget calculation, and recommended places logic.
- **`backend/main.py`** — presentation layer. Handles user input/output only and calls into `trip_service` for all business logic.

### Session 3 — Teaching KelanaAI to Communicate (REST API)

`backend/main.py` is now a **FastAPI** web service instead of a console app. It reuses the Session 2 business logic in `trip_service.py` and exposes it over HTTP.

### Session 4 — Teaching KelanaAI to Remember (PostgreSQL Persistence)

The app is now **stateful**: trip data is persisted to a **PostgreSQL** database using **SQLAlchemy** as the ORM, instead of only living in memory for the duration of a request.

- **`backend/database.py`** — database connection layer. Creates the SQLAlchemy engine and session factory from the `DATABASE_URL` in `.env`, and initializes tables on startup.
- **`backend/models/trip.py`** — SQLAlchemy ORM model for the `trips` table.
- **`backend/main.py`** — full CRUD (Create, Read, Update, Delete) for trips, backed by PostgreSQL. `PUT` recalculates `category` and `daily_budget` from the new budget before saving, and both `PUT` and `DELETE` return `404` when the trip id does not exist.

### Session 5 — Teaching KelanaAI to Think with AI (Amazon Bedrock)

KelanaAI moves from rule-based logic to **AI-native**: itineraries are generated by **Amazon Bedrock** and stored back into PostgreSQL.

- **`backend/services/bedrock_service.py`** — AI layer. Builds an enriched prompt that forces a structured daily plan for every day of the trip:
  - **Morning** — 2 to 3 specific activities
  - **Afternoon** — a cultural site plus a hands-on local experience
  - **Evening** — a dinner spot with a dish to order, plus nightlife or entertainment
- **`backend/models/trip.py`** — adds `ai_recommendation = Column(Text, nullable=True)` to store the generated itinerary.
- **`backend/main.py`** — `POST /api/v1/trips/{id}/generate` calls Bedrock and saves the result into `ai_recommendation`.

### Session 6 - Giving KelanaAI a Face (Next.js Frontend)

KelanaAI finally has a homepage. `frontend/` is a **Next.js 15 (App Router)** app styled with
**Tailwind CSS v4**, talking to the FastAPI backend over HTTP.

- **`frontend/app/page.tsx`** - the homepage: hero, planner, destinations, how-it-works, footer.
- **`frontend/components/Hero.tsx`** - full-bleed **hero image** with a dark gradient overlay so the
  headline stays readable on any photo.
- **`frontend/components/TripPlanner.tsx`** - the trip form. Creates a trip via
  `POST /api/v1/trips`, then generates the itinerary via `POST /api/v1/trips/{id}/generate`.
- **`frontend/components/DestinationGrid.tsx`** - responsive destination cards; picking one
  prefills the planner.
- **`frontend/components/Footer.tsx`** - copyright line plus product, developer and company links.
- **`frontend/lib/api.ts`** - typed API client with friendly errors when the backend is not running.

**Responsive layout:** the form is a 12-column grid from the `md` breakpoint up and collapses to a
single stacked column on mobile; the destination grid runs 1 / 2 / 3 columns across
mobile / tablet / desktop. Verified at 390px with no horizontal overflow.

**Backend change:** `backend/main.py` now installs FastAPI's `CORSMiddleware`. Without it the
browser blocks every request from the Next.js origin, so the frontend could not read any response.
Allowed origins come from the optional `FRONTEND_ORIGINS` env var and default to
`http://localhost:3000,http://127.0.0.1:3000`.

### Session 7 - Connecting KelanaAI's Brain and Face (Trip History Dashboard)

KelanaAI becomes a multi-page app. `/dashboard` reads every saved trip back out of
PostgreSQL and renders it as a rich trip card.

- **`frontend/app/dashboard/page.tsx`** - the trip history route.
- **`frontend/components/TripDashboard.tsx`** - fetches `GET /api/v1/trips`, shows summary
  stats, and handles the loading, empty and API-unreachable states.
- **`frontend/components/TripCard.tsx`** - one saved trip: country flag, `USD 2,000`-style
  budget, colour-coded category badge and a travel style badge.
- **`frontend/components/Pagination.tsx`** - kicks in past 10 trips per page, collapsing long
  page lists to `1 ... 4 5 6 ... 12`.
- **`frontend/lib/trip-display.ts`** - the shared presentation rules (destination to country
  code, currency formatting, badge colours) used by both the planner and the dashboard.

**Travel style:** the badge needed real data to show, so `travel_style` (`Solo`, `Couple`,
`Family`) was added to the `trips` table, to `POST /api/v1/trips`, and to the planner form.
The value is validated with `Literal`, so an unknown style gets a `422` instead of being stored.
Trips saved before this column existed stay `NULL` and render a neutral "Style not set" badge
rather than being backfilled with a style nobody chose.

**Flags:** destinations map to ISO country codes and render as flag images, not emoji. Windows
ships no country-flag font, so an emoji flag degrades to bare letters there - `getDestinationCountry`
returns `null` for unrecognised destinations and the card falls back to a neutral globe.

`GET /api/v1/trips` now returns newest first, which is the order a history view wants.

### Session 8 - Teaching KelanaAI to Know Its Users (Accounts and Ownership)

Trips stop being public. Every trip endpoint needs a bearer token, and every trip
belongs to exactly one account.

- **`backend/models/user.py`** - the `users` table. Only the bcrypt hash is stored.
- **`backend/services/auth_service.py`** - bcrypt hashing plus HS256 JSON Web Tokens.
- **`backend/main.py`** - `POST /api/v1/auth/register`, `POST /api/v1/auth/login`,
  `GET /api/v1/auth/me`, and a `get_current_user` dependency on every trip route.
- **`backend/test_ownership.py`** - runs the real app against a scratch SQLite file and
  asserts the rules below. Run `python test_ownership.py` from `backend/`.

**The ownership rules**

| Situation | Response |
|-----------|----------|
| No token, or a bad or expired one | `401` |
| `GET /api/v1/trips` | only the trips whose `user_id` is yours |
| `GET` / `PUT` / `DELETE` / `generate` on your own trip | `200` |
| The same calls on somebody else's trip | `403` |
| The same calls on a trip id that does not exist | `404` |

A trip that does not exist answers `404` while one you may not touch answers `403`,
exactly as the brief asks. Trips saved before accounts existed have `user_id = NULL`:
they belong to nobody, stay out of every list and answer `403`, rather than being
handed to whoever registers first.

**Frontend**

- **`components/AuthProvider.tsx`** - holds the session, restores it on load, and signs
  you out if the API ever rejects the token.
- **`components/RequireAuth.tsx`** - wraps `/plan`, `/dashboard`, `/trips/[id]` and
  `/profile`, sending signed-out visitors to `/login?next=<where they were going>`.
- **`components/AuthForm.tsx`** - the shared register and login form.
- `/` stays public; the planner moved to the protected `/plan`.

The route guard is a convenience, not the security boundary. The real protection is the
API: a visitor who bypasses the guard still gets `401`, and a signed-in user who opens
somebody else's trip id gets `403` with none of that trip's data in the response.

### Session 9 - Teaching KelanaAI to Read Knowledge (RAG)

KelanaAI gets a knowledge base and answers from it instead of from memory.

- **`backend/knowledge_base/`** - five markdown documents: service policies, budget
  playbook, Indonesia and Japan destination playbooks, and a safety runbook.
- **`backend/services/kb_service.py`** - retrieval plus two answer paths,
  `answer_with_rag()` and `answer_with_base_model()`.
- **`backend/services/fact_check.py`** - the scoring shared by both scripts.
- **`backend/scripts/sync_kb.py`** - uploads the documents to S3 and starts a Bedrock
  ingestion job. It never creates the bucket or the knowledge base.
- **`backend/scripts/check_retrieval.py`** - retrieval quality, no AWS needed.
- **`backend/scripts/compare_rag.py`** - the RAG vs base-model comparison.
- **`POST /api/v1/ask`** - answer a question from the knowledge base (`mode: "rag"`)
  or deliberately without it (`mode: "base"`). Requires a bearer token.
- **`GET /api/v1/kb/search?q=`** - retrieval only, no model call. Useful for debugging.

**Two retrievers.** Set `BEDROCK_KNOWLEDGE_BASE_ID` to query the managed Bedrock
Knowledge Base. Leave it empty and the same documents are searched in-process with
BM25, so retrieval can be developed and tested without an AWS account.

**Results.** See [docs/rag-vs-base-model.md](docs/rag-vs-base-model.md) for the raw
answers and scores, and [docs/rag-findings.md](docs/rag-findings.md) for what the
scores do and do not show. Measured with `amazon.nova-lite-v1:0`: RAG scored 14/23
facts, the base model 2/23. Reading the answers matters more than the totals - the
base model invented a KelanaAI refund policy, a four-tier budget scale that does not
exist, and a three-day Bali itinerary that KelanaAI will not sell.

Retrieval is checked separately from generation
([docs/retrieval-check.md](docs/retrieval-check.md)) because the two fail differently.
That split is what showed Q2's wrong answer to be a reasoning error rather than a
retrieval one: the right passage was in context and the model still misread it.

**Model calls use the Converse API.** `invoke_model` needs a different request body
per provider, so the old Anthropic-shaped body broke as soon as the model id pointed
at Amazon Nova. Converse takes the same shape for every model; `bedrock_service.py`
was migrated too.

### Session 10 - Teaching KelanaAI to Remember Conversations

Bedrock still has no memory of its own - "memory" is two new tables plus the backend
reassembling them into the model's context before every call.

- **`backend/models/conversation.py`** - `conversations` and `messages`. Every turn is
  stored; a conversation belongs to exactly one account, same ownership rule as trips.
- **`backend/services/kb_service.answer_conversation()`** - takes the full message
  history (oldest first), retrieves against only the latest user turn, and sends the
  whole history to Bedrock's Converse API so earlier turns are still in context.
- **`POST /api/v1/conversations`**, **`GET /api/v1/conversations`**,
  **`GET /api/v1/conversations/{id}`**, **`POST /api/v1/conversations/{id}/messages`**,
  **`DELETE /api/v1/conversations/{id}`** - all bearer-token gated, all `403` on
  someone else's conversation, same as trips.
- **`backend/test_conversations.py`** - 37 checks against the real app on SQLite, with
  `answer_conversation` swapped for a fake so no AWS account is needed to run it. It
  asserts the history sent to the model on the *second* message is exactly the four
  prior turns in order plus the new one - that reassembly is what "memory" means here
  - and that a Bedrock failure keeps the traveller's own message instead of losing it.
  `python test_conversations.py` from `backend/`.

**A timezone bug the tests caught.** `MessageResponse`/`ConversationSummary` now run a
`field_validator` that stamps UTC onto any naive datetime before it leaves the API.
SQLite (unlike PostgreSQL's `TIMESTAMPTZ`) does not preserve `tzinfo` on read, so a
timestamp written as UTC came back from the ORM naive and serialized with no `Z` or
offset - a browser more than a few minutes from UTC then read it as local time. On a
UTC+7 machine, a message sent seconds ago showed as "7 hours ago". The Python test
suites never caught it because they only check that a timestamp is present, not what a
browser does with it; a live browser check against the real API did.

**Frontend chat interface** - the four requested UX pieces:

- **Conversation title** - the traveller's first message, shown at the top of
  `components/ChatWindow.tsx`; `"New conversation"` until it exists.
- **Auto-scroll** - instant to the bottom on opening an existing conversation, smooth
  for every message after that (including the typing indicator appearing), and it
  overrides a manual scroll-up the moment a new message arrives.
- **Typing indicator** - three bouncing dots (`components/TypingIndicator.tsx`) shown
  as an assistant-side bubble from the moment a message is sent until the reply lands.
- **Timestamp per bubble** - `lib/chat-display.ts` formats each message's time
  (`"14:32"`, or `"Sep 3, 14:32"` once it is no longer today) and each conversation's
  last-active time on the `/chat` list (`"3 hours ago"`).
- **`app/chat/page.tsx`** - the conversation list, and **`app/chat/[id]/page.tsx`** -
  one conversation, both behind `RequireAuth`.

The composer sends the message optimistically (shows it before the server confirms),
and if the reply fails, drops the optimistic bubble and puts the text back in the
composer rather than losing it - the backend still keeps the traveller's message
either way, per `_append_message_and_reply()`'s design.

## How to Run

1. Copy `.env.example` to `.env` and fill in your PostgreSQL connection string and AWS settings:

   ```
   DATABASE_URL=postgresql+psycopg2://<user>:<password>@localhost/kelana_ai
   AWS_REGION=us-east-1
   BEDROCK_MODEL_ID=anthropic.claude-3-5-sonnet-20240620-v1:0
   AWS_ACCESS_KEY_ID=<your key>
   AWS_SECRET_ACCESS_KEY=<your secret>
   JWT_SECRET=<a long random string>
   ```

   `JWT_SECRET` signs every login token. Generate your own with
   `python -c "import secrets; print(secrets.token_urlsafe(48))"`. If it is left unset
   the app boots with a shared development secret and prints a warning, and anyone who
   knows that default can mint a token for any account.

   The Bedrock model you pick must be **enabled in your AWS account for that region**
   (Amazon Bedrock console → Model access).

2. Install dependencies and start the server:

   ```bash
   cd backend
   pip install -r requirements.txt
   uvicorn main:app --reload
   ```

The API will be available at `http://127.0.0.1:8000`, and interactive Swagger docs at `http://127.0.0.1:8000/docs`.

## Authentication

Create an account, then use the returned token on every trip request.

```bash
# 1. Register (or POST to /api/v1/auth/login if you already have an account)
curl -X POST http://127.0.0.1:8000/api/v1/auth/register   -H "Content-Type: application/json"   -d '{"email":"you@example.com","password":"at-least-8-chars","full_name":"You"}'

# 2. Use the access_token it returns
curl http://127.0.0.1:8000/api/v1/trips   -H "Authorization: Bearer <access_token>"
```

Passwords are hashed with bcrypt and never stored or returned in plain text. Tokens are
signed with HS256 using `JWT_SECRET` and expire after `JWT_TTL_HOURS` (24 by default).

To check the ownership rules yourself:

```bash
cd backend
pip install httpx        # only needed for the test file
python test_ownership.py
```

## Knowledge Base

Five markdown documents in `backend/knowledge_base/` hold KelanaAI's own operating
knowledge: policies, budget rules, destination playbooks and the safety runbook.
They are deliberately internal - the point of a RAG test is to ask things a base
model cannot know, and public facts about Bali would not tell the two systems apart.

Where a document touches something set by a government (visa rules, eruption alerts,
tourist levies) it says so and points at the official source instead of asserting a
number. The knowledge base records how KelanaAI *plans*; it is not a substitute for
an embassy or a national agency.

```bash
cd backend

# Retrieval quality. No AWS needed.
python scripts/check_retrieval.py --out ../docs/retrieval-check.md

# Upload the documents to S3 and start a Bedrock ingestion job.
python scripts/sync_kb.py --dry-run     # list what would be uploaded
python scripts/sync_kb.py

# RAG vs base model. Ten Bedrock calls, writes docs/rag-vs-base-model.md.
python scripts/compare_rag.py
```

`sync_kb.py` needs `KB_S3_BUCKET`, and starts an ingestion job only when
`BEDROCK_KNOWLEDGE_BASE_ID` and `BEDROCK_DATA_SOURCE_ID` are both set. It never
creates the bucket, the knowledge base or the vector store, because a Bedrock
Knowledge Base carries a standing cost - provision those once, deliberately.

## Chat

`/chat` starts a conversation that remembers itself. Every message you send and every
reply is stored in PostgreSQL; before each new call, the backend reads that history
back and sends the whole thing to Bedrock, because the model itself keeps nothing
between calls. Retrieval for a reply runs only against your latest message, not the
full conversation, so an earlier unrelated question cannot dilute what is being asked
right now - but the model still sees every prior turn, so "and what about the balance?"
correctly resolves to whatever you were just discussing.

The interface:

- **Conversation title** at the top, taken from your first message.
- **Auto-scroll** - instant to the latest message when you open a conversation,
  smooth for every message after that.
- **Typing indicator** while a reply is on its way.
- **Timestamp** on every message bubble, and a "3 hours ago" style time on the
  conversation list.

Same ownership rule as trips: every conversation endpoint needs a bearer token, and
`403` if the conversation is not yours.

```bash
cd backend
python test_conversations.py   # 37 checks, no AWS account needed
```

## API Endpoints

Every `/api/v1/trips` endpoint requires an `Authorization: Bearer <token>` header.

| Method | Endpoint                        | Description                                                   |
|--------|----------------------------------|----------------------------------------------------------------|
| GET    | `/`                              | Welcome message                                                 |
| GET    | `/health`                        | Health check                                                    |
| POST   | `/api/v1/auth/register`          | Create an account, returns a token                              |
| POST   | `/api/v1/auth/login`             | Sign in, returns a token                                        |
| GET    | `/api/v1/auth/me`                | The signed-in account                                           |
| POST   | `/api/v1/trips`                  | Create a trip and get category + daily budget                   |
| GET    | `/api/v1/trips`                  | List **your own** trips, newest first                                            |
| GET    | `/api/v1/trips/{id}`             | Get one of your trips; `403` if not yours                                         |
| PUT    | `/api/v1/trips/{id}`             | Update your trip's budget; `403` if not yours   |
| DELETE | `/api/v1/trips/{id}`             | Delete your trip; `403` if not yours                                             |
| POST   | `/api/v1/trips/{id}/generate`    | Generate an AI itinerary for your trip; `403` if not yours    |
| POST   | `/api/v1/ask`                    | Answer from the knowledge base (`mode: rag`) or without it (`base`) |
| GET    | `/api/v1/kb/search?q=`           | Retrieval only, no model call                                   |
| POST   | `/api/v1/conversations`          | Start a new, empty conversation                                 |
| GET    | `/api/v1/conversations`          | List **your own** conversations, most recently active first     |
| GET    | `/api/v1/conversations/{id}`     | One conversation with its messages; `403` if not yours          |
| POST   | `/api/v1/conversations/{id}/messages` | Send a message, get a reply grounded in the full history    |
| DELETE | `/api/v1/conversations/{id}`     | Delete your conversation; `403` if not yours                    |
| GET    | `/api/v1/recommendations`        | List of recommended places                                      |
| GET    | `/api/v1/transportations`        | List of available transportation options                        |

## Input

`POST /api/v1/trips` expects a JSON body with:

| Field | Type | Description |
|----------------|---------|-------------------------------|
| `destination` | string | Destination name |
| `days` | integer | Number of travel days |
| `budget` | float | Total trip budget |
| `travel_style` | string | `Solo`, `Couple` or `Family`. Optional, defaults to `Solo` |

The owner is taken from the bearer token, never from the request body.

`PUT /api/v1/trips/{id}` expects a JSON body with:

| Field | Type | Description |
|----------------|---------|-------------------------------|
| `budget` | float | New total trip budget |

`POST /api/v1/trips/{id}/generate` takes no body — it reads the saved trip and asks Bedrock for an itinerary.
