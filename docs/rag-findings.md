# What the RAG comparison actually showed

A read of [rag-vs-base-model.md](rag-vs-base-model.md), which is generated by
`backend/scripts/compare_rag.py`. That file holds the raw answers and the
automated score. This one says what the score misses.

Run: `amazon.nova-lite-v1:0` in `ap-southeast-2`, local BM25 retriever over 5
documents / 39 chunks, temperature 0.

## Headline

| | Automated score | My read of the answers |
|-|-----------------|------------------------|
| RAG | 14/23 facts | 4 of 5 substantially correct, 1 wrong |
| Base model | 2/23 facts | 0 of 5 correct; 3 confidently wrong |

The automated score understates RAG and overstates nothing. Both numbers are
real; neither is the whole story.

## Per question

**Q1 — rebooking cap. RAG right, base model invented policy.**
RAG got the two things asked: three alternatives within 4 hours, USD 150 absorbed
per traveller. It scored 2/4 because it did not volunteer the two related rules
(anything above the cap is quoted first; the service fee is refunded if all three
are rejected). Those were in the retrieved context and would have made the answer
better, so the deduction is fair.

The base model scored 0/4 and deserved it. It produced six headed sections of
plausible-sounding policy — "KelanaAI might absorb the $100 difference", "you are
entitled to a reasonable number of alternatives" — none of which is KelanaAI's
policy. This is the failure mode that matters commercially: a support answer that
reads like it came from the handbook and did not.

**Q2 — budget category. RAG half wrong, and the error is instructive.**
RAG got the comfort floor exactly right: USD 900 over 20 days is USD 45 a day,
Yogyakarta's Backpacker allowance is USD 25, so the trip clears the floor. Then
it said the category is **Standard**. It is Backpacker — the threshold is under
USD 1,000, and the retrieved passage says so on the line above.

This is a reasoning error, not a retrieval error, and the split reporting is what
makes that visible: [retrieval-check.md](retrieval-check.md) confirms the
threshold table was in context. A bigger model, or a follow-up validation step,
would fix this; more documents would not.

The base model, asked the same thing, invented a four-tier scale
("Budget / Mid-Range / Comfort / Luxury") that does not exist in KelanaAI and
concluded the trip is "Mid-Range". Confident, structured, wrong.

**Q3 — Bali minimums. RAG fully correct; the scorer was too harsh.**
The answer — six nights minimum for two zones, two zones maximum in five days —
is exactly right and complete for what was asked. It scored 1/4 because the
rubric also lists supporting details (the half-day zone move, the 1.5-2.5 hour
South-to-Ubud drive) that the question never asked for.

I left the rubric alone rather than editing it after seeing the result. Loosening
a benchmark once you know the score is how benchmarks stop meaning anything. The
fix belongs in the rubric design, not in a post-hoc trim, and it is listed as a
next step below.

The base model said the shortest two-zone Bali trip is **3 days**. KelanaAI will
not sell that. This is the single clearest commercial case for RAG in the set: an
agent quoting the base model would be promising something operations has
explicitly ruled out.

**Q4 — Japan rail pass. RAG right, base model gave the answer the playbook exists to prevent.**
RAG said not to put a nationwide pass in an itinerary without showing the
point-to-point comparison, and gave the 7-night multi-city minimum. Scored 4/5;
the "missed" fact is the same rule in different words, so the real score is 5/5.

The base model produced a detailed JR Pass sales pitch with specific yen prices
and pass tiers. Those prices are stated with no date and no source, and the
playbook's whole point is that pass pricing moved enough to reverse KelanaAI's
default. This is the case where the base model is not vague but *actively
contrary to current company guidance*.

**Q5 — eruption escalation. RAG right on substance, thin on one detail.**
RAG correctly classified it S1 and reproduced the three-step script in order:
emergency services first, then the duty line, then stop planning. It scored 3/5
because it did not state the 15-minute response time and phrased the escalation
without the word "immediately".

The base model explained the generic volcanic alert colour scale (Green / Yellow
/ Orange / Red) and offered its own safety guidance. For a safety question that
is the worst possible behaviour: it neither escalates nor points at the national
agency, and KelanaAI's runbook explicitly forbids the assistant from assessing
whether a place is safe.

## Two things the numbers do not show

**The scorer under-credits paraphrase.** It checks that every number in a fact
appears and that 70% of the other words do. A correct answer in different words
loses points (Q3, Q4), and a fluent wrong answer loses none for being wrong — Q2
scored 4/5 while getting the headline category backwards. Treat the score as a
recall floor, not a grade.

**Grounded answers were stable; ungrounded ones were not.** Across three runs at
temperature 0, RAG scored 14, 14, 14. The base model scored 5, 2, 2 on the same
questions. Retrieval did not only make answers more correct, it made them
repeatable — which matters more than the average if these answers go to
travellers.

## What I would do next

1. **Fix the rubric properly.** Split `expected_facts` into *required* (must be
   in any correct answer) and *supporting* (credit if present). Q3 and Q5 are
   mis-scored today because the two are mixed.
2. **Add a correctness check, not just a coverage check.** A second model call
   grading each answer against the source passage would have caught Q2's
   inverted category, which keyword scoring structurally cannot.
3. **Ask the model to quote the threshold before applying it.** Q2's error came
   from applying a rule it had in front of it. Making the answer restate the rule
   first is a cheap prompt-level fix worth testing.
4. **Move to the managed Bedrock Knowledge Base.** The local BM25 retriever
   needed a rare-term guarantee before it would surface the Yogyakarta row at all
   (see below). Embeddings would likely handle that case without the special
   rule.

## Retrieval bugs found and fixed while building this

Both were found by running the retrieval check, before any model was called.

1. **A 14-row city table was one chunk, so no single city ranked.** Asking about
   Yogyakarta returned six passages about budgets in general and none containing
   the Yogyakarta row — it ranked #14. BM25 divides by chunk length, so one
   mention among fourteen cities lost to short chunks that merely shared the
   topic words. Fixed by splitting long markdown tables into row groups that each
   repeat the header, and by guaranteeing that a chunk mentioning a rare query
   term reaches the model.
2. **The fact checker passed facts that were absent.** It accepted a fact when
   70% of its words appeared, which passed "Yogyakarta's Backpacker allowance is
   USD 25 per day" against text containing neither "Yogyakarta" nor "25" — the
   filler words alone cleared the bar. Numbers are now required outright. This
   bug was hiding the first one: retrieval reported 23/23 facts covered while the
   Yogyakarta figure was genuinely missing.
